# AI Council review: PR 76 (`0e7f184` → `1fc8ae1`)

I found no blocking defects. The routing change matches its stated purpose, and the new tests cover it. Auto-detect now sends `microsoft/mai-transcribe-1.5` with `provider: { zdr: true }` and no `language`. An explicit language still uses the saved preferred model. The new HTTP messages contain only the status code, and the it.each test checks that nothing sensitive is serialized. I found four smaller issues, all introduced by this diff.

---

### 1. Medium: Transcription-specific advice in what is probably a shared error mapper (introduced)

- **Where:** `src/providers/openRouter/errors.ts`, `mapOpenRouterHttpError`, in the new `case 400/422`, `case 404` and `case 413` branches.
- **Evidence:** The messages are written for transcription: "try a shorter recording", "for Auto-detect, choose a specific recording language first" and "rejected the recording because it is too large". The function takes only `(status, payload)`, so it can't tell which request failed. Its location in the provider module suggests the translation workspace, Light cleanup and any model-catalog fetch use it too. The packet doesn't show the callers, so I can't confirm this.
- **Impact:** If the mapper is shared, a translation or cleanup request that gets a 404 or 400 would tell the user to change their recording language or shorten their recording. That advice is wrong and sends them to the wrong fix. A 404 from the model catalog in Settings would mention zero-data-retention routing, which wouldn't apply.
- **Smallest safe fix:** Add an optional `context: 'transcription' | 'chat' | 'catalog'` parameter, or let the transcription call site override the message. Show recording-specific text only for transcription; everything else gets a neutral `OpenRouter rejected the request (HTTP ${status}).`
- **Verification:** Find every call site of `mapOpenRouterHttpError`. Add tests that a cleanup or translation 404/400 doesn't contain "recording" or "Auto-detect".

### 2. Low–Medium: HTTP 403 is now treated as an authentication error (introduced)

- **Where:** `errors.ts`, `case 403` returns `'auth_error'`; the test table row `[403, 'auth_error', false]`.
- **Evidence:** Before this diff, 403 fell through to `default` and became `unknown`. OpenRouter also returns 403 for reasons unrelated to the key, such as moderation-flagged input and some provider or policy denials.
- **Impact:** Any code that reacts to `auth_error` would wrongly blame the user's API key. That could mean an "update your API key" prompt, a re-auth flow or clearing a credential. The message text is hedged, but the category isn't.
- **Smallest safe fix:** Map 403 to `'unknown'` (or a new `'forbidden'` category) and keep the current message. Or first confirm nothing branches on `auth_error` beyond displaying the message.
- **Verification:** Search for every use of `auth_error`. Add a test that a 403 doesn't trigger key invalidation or re-auth UI.

### 3. Low–Medium: Bottom tab labels can still get cut off at the largest iPhone text sizes (introduced, fix incomplete)

- **Where:** `src/App.tsx`, the tab `<Text>` (`adjustsFontSizeToFit`, `minimumFontScale={0.7}`, `numberOfLines={1}`) and `styles.tabLabel` (`width: '100%'`, `fontSize: 14`).
- **Evidence:** iOS accessibility text sizes can scale text by about 3×. Shrinking only to 70% can't fit four labels across a roughly 375 pt row with 8 pt padding, so iOS will truncate them with "…". No `maxFontSizeMultiplier` is set. If the tab bar has a fixed height (it isn't shown), the text may also be clipped vertically.
- **Impact:** The labels stay on one line as intended, but at the largest sizes they can become unreadable ("Transc…"). That works against the reason for enlarging the text in the first place.
- **Smallest safe fix:** Add `maxFontSizeMultiplier` (around 1.3–1.5) to the tab `Text`, and keep `adjustsFontSizeToFit`. Optionally offer a larger-text alternative for accessibility users, such as a long-press label.
- **Verification:** Check on a physical iPhone or simulator at default, the largest standard size and AX5. Add a render test asserting `numberOfLines === 1` and that `maxFontSizeMultiplier` is set.

### 4. Low: Support page sends older-app users to an error message they will never see (introduced, documentation)

- **Where:** `website/support/index.html`, the new heading "No eligible OpenRouter endpoint was found (HTTP 404)".
- **Evidence:** The paragraph is meant for users still on older app versions that use GPT-4o Transcribe. Those builds map 404 to the old generic "OpenRouter request failed." message. The test table already had `[404, 'unknown', false]`, and the new message ships only with this PR.
- **Impact:** The users with the actual problem won't find the section by matching their error text. The workaround (pick a specific recording language) is hidden from the very group it's for.
- **Smallest safe fix:** Add a sentence or subheading such as: "On older versions this appears as 'OpenRouter request failed.' when Auto-detect is selected."
- **Verification:** Check the page renders and its internal links resolve. Compare the wording with the shipped 1.1.x build.

I found no blocking defects in the packet. There are 5 actionable findings, all introduced by this diff except the one marked as partly pre-existing. I did not run any tools.

**1. Medium: Auto-detect now depends on an unproven model.**
- **Where:** `src/domain/transcriptionModelLanguages.ts`, `AUTO_DETECT_TRANSCRIPTION_MODEL_ID`.
- **Evidence:**
  - The old test asserted that `resolveTranscriptionModelId('microsoft/mai-transcribe-1.5', 'auto')` returned GPT-4o. So MAI was previously kept out of Auto-detect on purpose, and the diff doesn't say what changed.
  - The only support for MAI's language identification and Arabic/English behavior is the comment and the HTML note. Public catalog eligibility is not proof of a working transcription.
  - The updated test mocks `fetch` and returns Arabic text, so it only proves the request shape (`provider: {zdr: true}`, no `language`).
  - ZDR eligibility is hardcoded from a 2026-10-04 snapshot.
- **Impact:** MAI may translate to English, mis-detect languages, or lose its Azure ZDR route. If it does, every Auto-detect recording fails. There is no fallback.
- **Smallest fix:** Before release, run one real Auto-detect request in English and one in Arabic. Record the result in the fix doc or PR notes. Keep the ID as a single constant.
- **Verification:** The two live runs, plus the existing mocked integration test.
- **Origin:** Introduced.

**2. Low–Medium: the new HTTP error copy is too specific for every request type.**
- **Where:** `src/providers/openRouter/errors.ts`, `mapOpenRouterHttpError`, cases 400/422/404.
- **Evidence:** The mapper is shared. The 400/422 text says "try a shorter recording" and the 404 text says "choose a specific recording language first". The 404 text also assumes zero-data-retention routing and Auto-detect.
- **Impact:** A 404 or 400 from cleanup, translation, or model-list calls shows misleading advice about recordings and Auto-detect.
- **Smallest fix:** Keep the status code in the shared message, and move the transcription-specific hints to the transcription call site. Alternatively, pass an operation parameter to the mapper.
- **Verification:** Add tests that a cleanup 404 and a transcription 404 give different guidance.
- **Origin:** Introduced. The old generic message was safe but unhelpful.
- **Privacy:** The new messages interpolate only the numeric status. The tests also check that the sensitive-value payload stays out of the serialized error. I found no leak.

**3. Low–Medium: the tab-label fix is unverified at large accessibility text sizes.**
- **Where:** `src/App.tsx`, the tab `<Text adjustsFontSizeToFit minimumFontScale={0.7} numberOfLines={1}>`.
- **Evidence:**
  - Dynamic Type multiplies the 14pt font first, and `minimumFontScale` then shrinks only to 70% of that scaled size. At the largest accessibility sizes, "Transcribe" in a quarter-width tab can still overflow and clip.
  - No test covers these props, and no device test was done.
  - `adjustsFontSizeToFit` also behaves differently on Android.
- **Impact:** The single-line goal may fail at the largest text sizes.
- **Smallest fix:** Add `maxFontSizeMultiplier` (about 1.2–1.3) to the tab label.
- **Verification:** A render test for the props, and a manual iPhone check at the largest Dynamic Type and accessibility sizes, on both iOS and Android.
- **Origin:** Introduced. The earlier layout wrapped or truncated, which is the problem being fixed.

**4. Low: the model name is hardcoded in about eight places.**
- **Where:** `RecordScreen.tsx`, three strings in `SettingsScreen.tsx`, the setup page and the support page. These sit alongside the constant in `transcriptionModelLanguages.ts`.
- **Evidence:** The model changed once already, and this diff edits every copy by hand. The only copy test is the `RecordScreen` string.
- **Impact:** The next swap can leave stale copy, and the support page tells users which engine is in use.
- **Smallest fix:** Derive the display name in the app screens from one constant. Add a test that fails if `openai/gpt-4o-transcribe` appears in user-facing app strings.
- **Verification:** The new test, plus a grep.
- **Origin:** Introduced. Duplicated copy was already there before this diff.
